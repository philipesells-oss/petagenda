## Schema Detalhado

### Tabelas (Fase 1 MVP)

**tenants** — Pet shops (organizações)
- id, name, slug (unique), phone, email, address (jsonb), settings (jsonb)
- whatsapp_instance_id, whatsapp_connected, stripe_customer_id, stripe_subscription_id
- plan (starter/pro/business/trial), plan_status, trial_ends_at
- messages_used, messages_limit, created_at, updated_at

**users** — Funcionários do pet shop
- id (ref auth.users), tenant_id, full_name, role (owner/admin/employee)
- phone, avatar_url, is_active, permissions (jsonb)

**clients** — Donos dos pets
- id, tenant_id, full_name, phone, email, cpf, address (jsonb)
- tags (text[]), notes, total_spent, visit_count, last_visit_at
- loyalty_points, whatsapp_opt_in, status (active/inactive/blocked), inactive_since

**pets** — Animais
- id, tenant_id, client_id, name, species (dog/cat/bird/other)
- breed, size (small/medium/large/giant), weight, birth_date, gender
- coat_type, temperament, health_notes, photo_url, is_active

**services** — Catálogo de serviços
- id, tenant_id, name, description, duration_minutes, price
- price_by_size (jsonb), category (grooming/veterinary/daycare/other)
- color, is_active, sort_order

**appointments** — Agenda
- id, tenant_id, client_id, pet_id, service_id, assigned_to
- date, start_time, end_time, status (scheduled/confirmed/in_progress/completed/canceled/no_show)
- price, notes, confirmation_sent, reminder_sent, source, canceled_reason, completed_at

**business_hours** — Horário de funcionamento
- id, tenant_id, day_of_week (0-6), is_open, open_time, close_time, break_start, break_end
- UNIQUE(tenant_id, day_of_week)

**blocked_slots** — Bloqueios na agenda
- id, tenant_id, user_id (null = todos), date, start_time, end_time, reason

### Triggers
- `update_updated_at()` — atualiza updated_at em INSERT/UPDATE
- `update_client_metrics()` — incrementa total_spent, visit_count após appointment completed
- `auto_tag_client()` — tags automáticas (vip, novo, atrasado, inativo) antes de UPDATE em clients
- `handle_new_user()` — cria tenant + user após INSERT em auth.users

### RLS Helper
```sql
CREATE OR REPLACE FUNCTION get_my_tenant_id()
RETURNS UUID AS $$
  SELECT tenant_id FROM users WHERE id = auth.uid();
$$ LANGUAGE sql SECURITY DEFINER STABLE;
```

## Notas Técnicas

- Todas as tabelas com `tenant_id` precisam de RLS HABILITADO
- Policy padrão: SELECT/INSERT/UPDATE/DELETE filtrado por `get_my_tenant_id()`
- `handle_new_user()` deve ser SECURITY DEFINER para criar tenant sem estar autenticado
- Index `idx_no_overlap` em appointments para prevenir conflito de horário

### Decisões autônomas registradas

- **[AUTO-DECISION]** `supabase gen types typescript` requer PAT (Personal Access Token) — não disponível. **Reason:** o arquivo `src/types/database.ts` já existia (manual, Story 1.1) e refletia o schema 1:1. Apenas sincronizei adicionando `message_templates` (que foi incluído em 001 para suportar o seed 006). Alternativa (gen types automático) pode ser rodada depois pelo @devops com `SUPABASE_ACCESS_TOKEN`.
- **[AUTO-DECISION]** `update_client_metrics` implementado como **BEFORE UPDATE** (não AFTER) para conseguir setar `NEW.completed_at` defensivamente sem um UPDATE adicional. Reason: evita dead-tuple extra e mantém a operação idempotente.
- **[AUTO-DECISION]** `handle_new_user` usa `EXCEPTION WHEN OTHERS` com `RAISE WARNING` + `RETURN NEW`. Reason: nunca queremos bloquear um signup em `auth.users` por causa de erro de bookkeeping em `public`; a inconsistência pode ser reconciliada via job, mas signup não pode falhar.
- **[AUTO-DECISION]** `FORCE ROW LEVEL SECURITY` habilitado em `clients`, `pets`, `appointments`. Reason: dados mais sensíveis; mesmo o owner da tabela (postgres via Supabase dashboard) respeita RLS — previne vazamento via trigger/função não-SECDEF.
- **[AUTO-DECISION]** Connection via `db.{ref}.supabase.co:5432` (direct). Reason: pooler retornou `XX000` nos 3 endpoints testados. Direct funcionou. Para produção, DevOps deve revalidar e preferir pooler.
